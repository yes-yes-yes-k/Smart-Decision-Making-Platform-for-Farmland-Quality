# R2.5 抽取批次首轮运行（未通过，预算与模型不匹配）

日期：2026-10-31。按批准的 R2.4 方案执行十篇抽取。**结果：0 篇通过，7 次尝试消耗完预算，剩余 8 篇未运行。** 原因是推理型模型的思考 token 远超预算估算，不是协议缺陷。

## 授权的账

| 项 | 批准 | 实际 |
| --- | --- | --- |
| 尝试次数 | 20 | 7（v1 4 次、v2 3 次） |
| 预留 token | 60,000 | 56,709（v1）+ 53,905（v2 独立台账） |
| 实际计费 token | — | **24,259**（仅 1015 一次成功返回） |
| 通过篇数 | 10 | 0 |

两次运行的台账各自封顶，没有越界；v1 的四次全部超时，未产生实际用量，但台账按"未知用量按预留计"扣减，因此两个台账合计预留读数偏高（这是账本设计，不是多花）。

## 实际发生了什么

**v1（120s 超时）**：1015 连续两次超时（122s、120s），1021、104 各一次超时。四次都停在客户端等待，模型没有返回。
**诊断**：同一模型、同一端点，用 37 token 的极小请求 3.6 秒正常返回 `{"ok":true}`。端点和密钥没问题，是长提示词 + 推理开销导致慢。

**v2（300s 超时、max_tokens 1536）**：

| 文献 | 结果 | 耗时 | 用量 |
| --- | --- | ---: | --- |
| 1015 | `rejected: invalid_offsets` | 231.6s | 24,259（输入 4,303 / **推理 19,631** / 输出 325） |
| 1021 | 超时两次 | 300s ×2 | 无 |
| 其余 8 篇 | 预算守卫停止，未发送 | — | — |

## 三个硬事实

1. **单篇成本约 2.4 万 token，其中 81% 是推理 token**（19,631 / 24,259）。批准方案按"输入 3.9 万 + 输出 2 万"估算，十篇实际需要约 **24 万 token、40—60 分钟**，是批准的 4 倍。
2. **`max_tokens` 没有约束住推理开销**：设 1,536，实际 completion 19,956。该模型把推理算在 max_tokens 之外，预算无法靠调参压下来。
3. **协议是对的**：1015 返回后，`selection_protocol_v2` 判定 `invalid_offsets`（模型给的坐标与引文不匹配）并拒收，没有把错误记录当候选。这正是 R2.3 要拦截的情况。

## 一个值得改的方向（未执行）

1015 的拒收是"坐标错"而非"引文不存在"。可以让模型**只给引文、不给坐标**，由服务端用"块内唯一匹配"定位（R2.3 已实现该规则：不唯一则拒收）。这样能同时：

- 减少输出字段，降低出错面；
- 省掉坐标推理，可能显著压低推理 token；
- 与契约的"重复片段需显式位置"一致——唯一时可自动定位，不唯一时仍拒收。

但这会改变提示词与请求结构，需要重新冻结请求哈希，并且仍要重新授权预算。
