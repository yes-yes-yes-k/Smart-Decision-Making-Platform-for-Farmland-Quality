# R2.5 流式改造与超时归因（2026-10-31）

## 改了什么

新增 `framework/knowledge_graph/streaming_extraction_call.py`，把一次请求从一个"只回答快慢"的总时限，拆成四个可观测的闸门：

| 闸门 | 默认 | 说明 |
|---|---:|---|
| `ttft_limit` | 300s | 首个增量到达前允许的时间；超时即判定"请求被服务端扣住" |
| `gap_limit` | 180s | 相邻增量之间的最长间隔；区分"起步慢"与"中途卡死" |
| `total_limit` | 900s | 墙钟上限，取代原来的单一总时限 |
| `reasoning_cap` | 0（关） | 按实时推理估算中断失控的思维链，0 表示不限制 |

配套改动：

- 传输层 `read` 超时改为 `max(ttft, gap)`，即"多久没收到增量"，不再限制整体时长；
- 中断不吞内容：已收到的部分写入 `content_partial`，并带稳定原因码（`ttft_limit_exceeded` / `stream_gap_exceeded` / `total_time_limit_exceeded` / `reasoning_cap_exceeded` / `stream_truncated`）；
- 重试策略区分：`reasoning_cap_exceeded` 不重试（同一提示词会重复同样的跑飞），其余可重试一次；
- 每次尝试记录 `ttft_seconds`、`chunks`、`reasoning_characters`、`reasoning_tokens_estimated`，台账与检查点都能回溯；
- 推理估算系数按实测校准为 4.0 字符/token（原 2.6 高估 77%，会让上限提前触发）。

单元测试 10 项：正常收敛、流式参数下发、推理上限中断、上限关闭、块间停滞、首字超时、总量超限、无结束符、`model_extra` 中的推理字段、中断后保留部分内容。

## 验证（1 次真实请求）

`1149`，`thinking_budget=1024`、`max_tokens=4096`、6 块输入，运行 `r2-20261031-v17-stream-probe`：

| 指标 | 值 |
|---|---:|
| 首字耗时（TTFT） | **4.48s** |
| 总耗时 | 28.42s |
| 增量块数 | **2,163** |
| 吞吐 | 76.0 tok/s |
| 用量 | 4,134（输入 1,973 / 输出 2,161 / 推理 1,025） |
| 结果 | `accepted`，2 研究 / 2 实体 / 0 关系 |

## 结论

1. **推理是以增量下发的**：TTFT 4.5 秒、28 秒内 2,163 个块，说明服务端在处理过程中持续吐 reasoning delta，不是攒满再发。因此"600 秒超时是服务端排队"这一早前猜测**不成立**。
2. **吞吐与前几轮完全一致**（76 vs 69—86 tok/s），说明超时请求当时也在正常生成，只是生成量远超预期：按 76 tok/s 折算，600 秒对应约 **4.5 万** completion token，是典型值（1.9 万）的 2.4 倍。但下一节的 104 验证表明，对部分文献而言"生成更多"并不成立——它们根本不收敛。
3. **首字耗时从此可测**：以后再出现超时，`ttft_seconds` 大即排队，`chunks` 增长但总量爆掉即思维链跑飞，两者不再混成一个信号。
4. `thinking_budget=1024` 下关系为 0，与此前结论一致——低思考只能枚举实体。

## 未完成与口径说明
- **默认强度下的对照尚未跑**：还需一次 `reasoning_cap≈20000` 的请求，才能证明"超时＝思维链跑飞"在出问题的文献（104/1032）上同样成立。该请求约 2.2 万 token，超出本次验证批准的 5 千额度，待授权。
- **已超时的三次请求无法回溯归因**：它们是非流式调用，没有 TTFT 与块计数记录，只能从吞吐反推。
- **台账口径**：`Budget` 按 run 目录独立建库，本次 4,134 token 记在 `r2-20261031-v17-stream-probe` 自己的账本里，**不计入 A 阶段 22 万额度的台账**。跨 run 的总额度目前没有单一账本约束，属已知缺口。

## 104 验证（默认强度 + 推理上限 2 万）：未通过

`r2-20261031-v18-stream-104`，默认思考强度，`reasoning_cap=20000`，预算 3.2 万封顶：

| 尝试 | TTFT | 总耗时 | 增量块 | 推理字符 | 输出内容 | 结束状态 |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 3.20s | 118.5s | 11,604 | 48,701 | **0** | `stream_truncated` |
| 2 | 0.55s | 251.7s | 20,103 | 80,005 | **0** | `reasoning_cap_exceeded` |

两次共消耗 35,803（按预留口径），**一个字符的 JSON 都没产出**。

关键读数：

1. **不是排队**。两次首字分别是 3.20 秒与 0.55 秒，服务端几乎立刻开始下发。
2. **不是"慢但能完成"**。11,604 与 20,103 个增量块全部是 reasoning，`content` 为空，`finish_reason` 始终为 `None`。这篇文献在默认强度下**不收敛**——把超时从 600 秒加到 3,600 秒只会得到更贵的空结果。
3. **同一篇在低思考下能出结果**：`thinking_budget=1024` 时 44.92 秒返回、1 研究 / 3 实体 / 0 关系。说明文档本身可解析，发散发生在"无上限的思维链"这一段。
4. 第 1 次以 `stream_truncated` 结束（流被关闭、无结束符、无 usage），第 2 次是本地上限主动中断。两种终止方式都被正确归类，没有伪装成成功。

**处置**：104 记为 `reasoning_loop`，不再重试；关系缺口保留 v11 的低思考结果（0 关系）。这类文献需要的是提示词层面的收敛约束或分段抽取，不是更大的超时窗口。
