# 项目总纲

## 1. 项目定位

本项目的长期目标，不是单纯做一个县域演示页面，也不是只做某一个土壤模型接口，而是逐步建设一个面向耕地质量管理场景的智能化能力底座。这个底座未来要能够支撑数据整合、空间展示、专业诊断、方案生成、知识检索以及 Agent 调用编排，最终形成一个可持续扩展的耕地质量智能系统。

当前仓库的职责，不是替代历史项目，也不是一次性完成全量平台，而是承载新的集成层、能力层和后续 Agent 接入底座。

## 2. 业务背景与核心问题

当前希望解决的不是单点模型计算，而是耕地质量管理中的一组综合性问题：

- 耕地质量当前处于什么状态
- 主要限制因素是什么
- 哪些区域需要优先治理
- 可以采取哪些治理和提升措施
- 如何把分析结果进一步转化为汇报材料、决策支撑和后续自动化能力

因此，这个项目的真实目标是把耕地质量相关的数据、模型和知识能力，逐步沉淀成可复用、可组合、可被后续 Agent 调用的系统能力。

## 3. 长期目标

长期来看，系统应逐步具备以下五层能力：

1. 数据底座层
   统一整理调查数据、监测数据、地块数据、边界数据、项目数据、政策资料和模型输入资产。

2. 专业能力层
   沉淀耕地质量评价、障碍识别、酸化分析、有机质提升、综合改良等专业分析能力。

3. 结构化接口层
   将地图总览、诊断分析、结果整理、报告生成等能力，以稳定、机器可读的接口形式对外暴露。

4. 知识与解释层
   将政策、标准、技术规程、经验规则和模型解释信息整理为后续可被检索和引用的知识资产。

5. Agent 编排层
   在前述能力稳定后，由 Agent 通过工具调用或工作流编排的方式，完成多步分析、解释、汇总与决策辅助。

## 4. 当前阶段定位

当前阶段处于“基础能力引导期”，重点不是智能交互效果，而是先把未来 Agent 所依赖的底座打稳。

当前阶段的核心目标是：

- 围绕乐昌市样例数据，形成一个县域级的最小能力闭环
- 先建设结构化接口，而不是开放式对话能力
- 保证接口可独立运行、可验证、可扩展
- 为未来下一阶段的 Agent 接入保留清晰的输入输出契约

当前已经落地的首个 change 是：

- `bootstrap-lechang-county-demo`

这个 change 的职责是为后续系统打基础，而不是代表最终系统形态。

## 5. 当前 change 与长期目标的关系

`bootstrap-lechang-county-demo` 解决的是长期目标中的“结构化接口层”起步问题，主要承担以下职责：

- 定义乐昌市县域范围内的最小能力闭环
- 将总览、诊断、结果整理三类能力转为可调用接口
- 明确非侵入式集成边界
- 验证当前仓库可以独立承载这些能力，而不是依赖历史项目在线运行

它完成后，并不代表整个系统目标已经完成，只代表“基础能力接口底座”迈出了第一步。

## 7. 当前仓库的系统边界

当前仓库后续应重点承载以下内容：

- 乐昌市样例数据的组织、映射和派生资产
- 面向未来 Agent 的结构化接口契约
- 总览、诊断、结果整理等基础能力实现
- 来源可追溯、错误可解释、状态可机读的返回规范
- 后续可扩展的知识、报告和工作流封装

当前仓库不应承担以下职责：

- 直接作为历史项目的补丁仓库
- 依赖多个外部项目同时启动才可工作
- 在基础能力未稳定前，过早追求大模型自由对话体验

## 8. 后续阶段建议路线

在 `bootstrap-lechang-county-demo` 完成后，后续工作建议按以下顺序推进：

### 阶段一：基础能力稳定化

- 固化结构化接口契约
- 明确最小运行资产包
- 跑通独立运行与异常回退验证

### 阶段二：能力扩展

- 扩展更多诊断主题或专业模型
- 增补知识解释、来源说明和指标映射能力
- 形成可复用的报告输出和结果汇总能力

### 阶段三：Agent 接入准备

- 为接口补充工具描述、调用顺序和鉴权约束
- 明确 Agent 的输入参数规范和可组合流程
- 支持 Agent 将多个能力串联为完整分析链路

### 阶段四：范围扩展

- 从乐昌市扩展到更多县域
- 从单类问题扩展到更完整的耕地质量问题域
- 逐步向更高层级场景延伸

## 9. 未来提案必须继承的上下文

后续任何新的 OpenSpec change，在立项时都应默认继承以下事实，而不需要每次重新从会话中恢复：

- 目标系统是“耕地质量智能能力底座”，不是单次 Demo 页面
- 当前阶段优先级是“结构化基础能力”高于“智能体表现”
- 历史项目只可参考，不可侵入，不可作为运行时依赖
- 乐昌市是当前最合适的起步样例区域，但不是最终边界
- 每一个 change 都应说明自己是在长期路线中的哪一层、补的是哪一块能力

## 10. 建议的持续沉淀机制

为避免后续再次依赖单次会话，建议采用以下沉淀方式：

1. `openspec/project.md`
   记录长期不变或变化较慢的项目总纲、边界、阶段目标和继承上下文。

2. `openspec/changes/<change-id>/`
   记录某一次 change 的局部目标、设计、任务与规格。

3. 如后续阶段明显增多，可再增加一份“路线图/决策日志”文档
   用于记录跨多个 change 的重大决策、阶段切换原因和未决问题。

当前我建议先以 `openspec/project.md` 作为一级总纲即可。后续如果你发现跨 change 的决策越来越多，再补一个单独的“长期路线与决策记录”会更合适。
