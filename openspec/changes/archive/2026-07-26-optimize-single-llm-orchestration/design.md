## Context

当前专业智能体在 `answer_question` 中调用 RAG + LLM。一个农户问题会按依赖顺序执行 model-4、model-5、model-6，导致至少三次串行上游调用；任一调用的超时和重试都会累积到 API 总时延。专业智能体同时具备规则计算和模拟数据回退，因此 LLM 不应是生成可用业务结果的前置条件。

## Goals / Non-Goals

**Goals:**

- 将多智能体路线的 LLM 调用收敛为专业结果完成后的单次总结调用。
- 为 LLM 设置可配置的短超时和有限重试，并记录每次调用耗时。
- LLM 不可用时，继续返回完整的专业智能体汇总结果。

**Non-Goals:**

- 不改变角色路由、问题类型识别、专业模型规则或 API 响应结构。
- 不改造纯 RAG 路线的检索与单次 LLM 调用策略。
- 不引入队列、流式响应、缓存或新的第三方依赖。

## Decisions

### 决策 1：专业智能体默认关闭 RAG + LLM 生成

`BaseAgent._generate_with_rag` 新增 `enable_llm` 开关，默认关闭。专业智能体沿用现有规则和计算回退路径，确保 model-4、model-5、model-6 等执行不再产生串行外部请求。

备选方案是将各智能体并发调用 LLM。该方案仍会按请求数消耗上游额度、增加失败面，且依赖智能体的执行顺序无法完全并发，因此不采用。

### 决策 2：编排末尾只调用一次 LLM

`llm_generate` 在所有多智能体问题类型上运行，并把问题与结构化专业结果交给 LLM 生成最终答复。纯 RAG 路线不经过该节点，保持原有行为。

这样 LLM 仅用于表达整合而非业务推理前置条件，减少单个请求的上游调用次数。

### 决策 3：LLM 成功才覆盖专业摘要

结果聚合仅在 `llm_response.success` 为真且有内容时采用 LLM 输出；否则保留 `agent_summary`。因此超时、鉴权错误或网络错误不会把已经完成的专业结果替换为空答复或错误文本。

### 决策 4：短超时、零重试和调用日志

新增 `SILICONFLOW_LLM_TIMEOUT`（默认 20 秒）和 `SILICONFLOW_LLM_MAX_RETRIES`（默认 0）。服务记录调用开始、提示长度、历史消息数量、成功/失败和耗时。较短的单次预算优先保证聊天响应可控；需容忍更慢模型时可通过环境变量调整。

## Risks / Trade-offs

- **[风险] 专业智能体不再逐个引用知识库文档** → 纯 RAG 路线不变；多智能体路线优先使用专业规则结果，后续可单独设计共享检索上下文。
- **[风险] 最终 LLM 超时** → 聚合器返回已经生成的专业摘要，且日志标识失败类型和耗时。
- **[风险] 20 秒不适合个别慢模型** → 部署时可增大 `SILICONFLOW_LLM_TIMEOUT`，但不建议默认开启重试。

## Migration Plan

1. 在部署环境保留默认配置或显式设置 `SILICONFLOW_LLM_TIMEOUT=20`、`SILICONFLOW_LLM_MAX_RETRIES=0`。
2. 重启后端进程，使新的 LLM 客户端配置和编排策略生效。
3. 观察 `[LLM] 调用开始/成功/失败` 日志和 `/api/v1/chat/` 总耗时。
4. 如需回滚，恢复专业智能体的 `enable_llm=True` 调用方式并移除新增配置；不涉及数据库迁移。
