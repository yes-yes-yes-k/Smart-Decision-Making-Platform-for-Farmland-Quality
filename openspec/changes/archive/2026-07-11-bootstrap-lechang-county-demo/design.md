## Goals / Non-Goals

**Goals:**

- 在乐昌市范围内形成一组可运行、可调用、可验证的县域基础能力接口。
- 通过总览接口、诊断接口和结果整理接口，先把“数据和模型能力如何被外部调用”定义清楚。
- 最大化参考既有项目的空间分析和酸化诊断能力，减少首版自研范围。
- 将后续实现拆分为清晰的集成层、数据适配层和接口层，便于未来接入 Agent、前端或工作流系统。
- 保证当前仓库可以独立运行，不依赖历史项目进程、数据库或服务常驻。

**Non-Goals:**

- 不在首版中实现全省级多区域运营能力。
- 不在首版中统一接入六大专业模型的全部真实计算链路。
- 不在首版中建设正式的权限、租户、任务调度和在线训练体系。
- 不要求首版接入真实通用大模型或自然语言智能体。
- 不要求首版先完成复杂前端交互或对话体验。
- 不修改 `AcidMap` 或 `AcidificationModel/api` 的源码。
- 不以运行 `AcidMap` 或 `AcidificationModel/api` 为当前仓库能力生效前提。

## Decisions

### 决策一：首版只做“乐昌市县域基础能力接口版”

选择理由：

- 当前可直接使用的数据明确集中在乐昌市，且已有位置最近邻样例也围绕乐昌构建。
- 县域尺度足以支撑地图、诊断和报告接口的最小闭环，不会因多区域适配拉长周期。
- 对后续 Agent 来说，县域层级已经可以覆盖区域级诊断、总览和汇报生成的主要调用场景。

备选方案：

- 省级总览优先：范围大，但现有样例数据和模型调用链条不完整，接口定义容易失真。
- 地块级优先：粒度细，但需要更严格的数据精度与定位逻辑，不适合作为首个接口目标。

### 决策二：当前仓库承担“基础能力集成层”，不直接合并历史项目

选择理由：

- `AcidMap` 与 `AcidificationModel/api` 的技术栈、运行方式和数据依赖不同，直接合并成本高。
- 单独建立一个集成层，可以通过离线资产整理、代码迁移重写、结果样例固化或本地适配脚本形成当前仓库自己的能力实现，再对外暴露统一契约。
- 这样可以避免首版就破坏已有项目的稳定性，同时为未来 Agent 保持单一调用入口。

备选方案：

- 在 `AcidMap` 内直接堆叠全部逻辑：地图能力强，但酸化诊断和结果整理能力迁移成本高。
- 在 `AcidificationModel/api` 内增加地图接口：诊断能力强，但空间底图和图层组织不是其主场。

### 决策三：历史项目只作为“参考资产来源”，不作为运行时依赖

选择理由：

- 用户明确要求当前方案非侵入式，因此不能通过修改历史项目源码来补齐能力。
- 若当前仓库依赖历史项目在线运行，部署、调试和交付都会被历史项目环境绑定，违背“独立可运行”的目标。
- 将必要资源、数据结构、算法思路和可合法迁移的局部实现吸收到当前仓库，更利于形成清晰边界。

备选方案：

- 直接调用历史项目 HTTP 接口：接入快，但把当前能力建立在外部服务可用性之上，不满足独立运行要求。
- 通过 Git 子模块或包依赖直接引用历史项目代码：维护方便，但仍会形成版本耦合和运行耦合。

### 决策四：数据侧先做“接口输入资产 + 字段映射”，不先建设完整数据中台

选择理由：

- 现有数据来源多、字段未统一、还会持续更新，首版更适合定义一套稳定的演示输入资产。
- 基础数据包可以包含边界、掩膜、样点、指标派生表和接口示例入参，足以支撑接口实现与联调。
- 等到接口契约确认后，再回头固化生产级 ETL 和数据治理规则更稳妥。

备选方案：

- 先做统一库表与完整 ETL：长期正确，但前期工作量大，阻碍基础能力尽快出样。

### 决策五：首版采用“结构化接口 + 机器可读返回”，不先做自然语言交互

选择理由：

- 当前没有 Agent，因此先定义结构化输入输出，才能保证未来调用链稳定。
- 机器可读返回更利于后续 Agent 做工具调用、状态拼装、二次总结和多步编排。
- 在无知识库、无提示词体系的情况下，这种方式更可控，也更容易做接口级验证。

备选方案：

- 直接接入开放式大模型：表达能力更强，但当前缺少调用主体和稳定评估方式，风险更高。

## Risks / Trade-offs

- [数据字段不统一] → 先建立演示字段映射表，明确哪些字段属于“必须有”、哪些允许模板回退。
- [两个历史项目接口契约不一致] → 在集成层定义统一输入输出契约，优先包一层适配器，而不是修改源系统核心逻辑。
- [对历史项目形成隐式运行依赖] → 明确列出本仓库运行所需的本地资产、样例数据和迁移代码，禁止把外部服务存活作为成功条件。
- [接口输出偏展示、不利于 Agent 使用] → 统一要求返回结构化字段、来源信息和错误码，而不是只返回自然语言文本。
- [用户期待的是全省级平台] → 在文档中明确“县域基础能力接口版”定位，把扩展路径写清楚，避免误解为最终形态。
- [未来接入真实 Agent 时参数不稳定] → 首版先固化参数命名、默认值和缺失值回退规则，后续 Agent 直接基于该契约接入。

## Migration Plan

1. 先整理乐昌市演示数据包和字段映射，输出可被地图侧和诊断侧共同消费的基础资产。
2. 在当前仓库实现基础能力集成层，通过本地资产、迁移实现或重写实现形成地图能力、诊断能力和报告整理能力。
3. 先以结构化入参与响应样例打通端到端链路，完成接口级联调和验证，并确认整个流程不依赖历史项目在线运行。
4. 等未来 Agent 方案明确后，再在这些基础接口之上补充工具描述、调用封装和工作流编排。

回退策略：

- 如果能力迁移成本过高，首版允许退化为“预计算结果 + 静态图层 + 结构化返回”的半动态接口版，保证能力底座可交付，且仍不依赖历史项目在线运行。
