## Context

当前仓库的业务实现很轻量，核心只有四类能力：

- `get_county_overview`：返回县域与图层元数据。
- `diagnose_county`：返回按主题组织的结构化诊断结果。
- `build_report_summary`：将诊断结果整理为汇报摘要。
- `verify_standalone_runtime`：验证当前仓库不依赖历史项目在线运行。

这套结构已经满足“基础能力接口 Demo”的目标，但还没有把“多模型协同”表达为单独的调用层。结合你提供的文档，当前缺口不是算法复杂度，而是能力表达方式：

1. 仓库里还没有一份固定的 6 模型目录，外部无法知道有哪些专题模型可调。
2. 当前诊断接口按业务主题返回结果，不等于“一个大模型可以像调工具一样去调 6 个专题模型”。
3. Demo 阶段并不需要真实模型精度，但需要稳定、统一、可追溯的结构化契约，方便后续大模型统一组织。

## Goals / Non-Goals

**Goals**

- 为 6 个专题模型建立稳定的模拟调用契约。
- 让调用方能够先列出可用模型，再按统一结构化入参调用任一模型。
- 保证每个模型结果都能返回推荐图层、摘要、关键发现、治理建议、来源说明和可靠性标记。
- 将“多项协同提升模型”定义为组合型模型，能够清晰声明它综合了哪些上游专题结果。
- 保持当前仓库离线、独立、可验证的 Demo 属性。

**Non-Goals**

- 不在本次 change 中引入真实空间分析、真实统计建模或真实治理算法。
- 不要求本次 change 直接接入外部通用大模型、MCP 工具系统或工作流引擎。
- 不把现有 `diagnose_county` 重构成专题模型的唯一入口。
- 不扩展到乐昌市以外的县域或省级运行。
- 不修改历史项目源码，也不依赖其在线服务。

## Decisions

### 决策一：新增独立的“专题模型目录与调用层”，而不是复用现有诊断接口假装成 6 个模型

选择理由：

- 现有 `diagnose_county` 面向的是县域诊断主题，不是模型注册表。
- 大模型或 Agent 调工具时，更需要“列举模型”和“按 `model_id` 调用模型”的稳定契约。
- 将专题模型单独建层后，后续替换真实模型时可以只替换实现，不必重写调用方式。

备选方案：

- 直接把 `diagnose_county(topic=...)` 当作 6 个专题模型使用：实现快，但主题语义和模型语义混在一起，不利于后续扩展和统一编排。

### 决策二：6 个模型统一使用同一套输入输出骨架

建议固定以下 6 个 `model_id`：

- `spatial-structure-analysis`
- `soil-indicator-analysis`
- `obstacle-factor-identification`
- `acidification-governance`
- `organic-matter-improvement`
- `multi-factor-collaborative-improvement`

统一输入骨架建议包含：

- `model_id`
- `area_code`
- 可选 `longitude` / `latitude`
- 可选 `indicators`
- 可选 `context`

统一输出骨架建议包含：

- `status`
- `model`
- `area`
- `summary`
- `findings`
- `recommended_layers`
- `recommendations`
- `lineage`
- `reliability`
- `fallback`

选择理由：

- 这能最大化降低大模型侧的工具学习成本。
- 统一骨架便于测试、HTTP 封装和后续真实模型替换。
- 即使 6 个模型关注点不同，也可以通过 `findings`、`context`、`fallback` 等字段吸收差异。

### 决策三：协同提升模型显式声明依赖的上游模型，而不是伪装成独立无来源结论

选择理由：

- 文档明确指出“耕地质量多项协同提升模型”是综合各专题模型结果形成建议。
- Demo 阶段即使不真的执行复杂聚合，也应在输出中返回 `dependent_models` 或等价字段，说明它综合了哪些专题输出。
- 这样可以保持未来真实多模型编排的迁移路径。

备选方案：

- 让协同提升模型直接返回一段综合建议，不声明来源：实现更省事，但不利于可解释性和未来替换。

### 决策四：所有模型结果必须显式标注 `demo_stub`

选择理由：

- 当前仓库现有接口已经使用 `demo_stub` 可靠性等级。
- 6 个模拟模型如果不显式声明占位属性，最容易被误解为真实专业模型。
- Demo 阶段的关键价值是验证调用契约，而不是制造“仿真得像真实模型”的错觉。

## Risks / Trade-offs

- [模型数量增加但结果仍是占位] → 通过统一的 `reliability` 和 `lineage` 字段强调其 Demo 属性。
- [与现有诊断接口职责重叠] → 将专题模型层定义为“可被大模型调用的工具层”，将县域诊断层保留为业务聚合接口。
- [协同模型容易写成空泛总结] → 要求其显式返回依赖模型标识和分区分类建议，避免只有自然语言摘要。
- [后续真实模型输入差异较大] → 先统一最小输入骨架，差异字段通过 `context` 或 `indicators` 扩展。
- [HTTP / CLI / Python API 三层契约漂移] → 统一由同一模型调用层输出结构，外层仅负责参数转发。

## Migration Plan

1. 先定义模型目录、模型标识和统一返回骨架。
2. 再实现 5 个单主题模拟模型与 1 个协同模型。
3. 将模型目录与调用入口暴露给 Python API，并同步接入现有 CLI / HTTP。
4. 最后补充测试和调用示例，确保未来大模型可以直接把这些模型当工具调用。

回退策略：

- 如果协同模型首版难以稳定组合多个上游结果，可以先输出固定依赖列表和占位综合建议，但不能省略依赖声明和 Demo 标记。

## Open Questions

- 首版是否需要让现有 `diagnose_county` 直接调用这些模拟专题模型，还是先保持两套入口并行存在？
- 大模型未来更可能通过 Python 函数、HTTP 接口还是 MCP 工具调用这些模型？这会影响后续接入层的优先级，但不影响本次契约设计。
