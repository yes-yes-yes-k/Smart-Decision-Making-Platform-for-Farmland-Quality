## 1. 建立线上基线与请求时间线

- [ ] 1.1 为 `/api/v1/chat/` 与 `/stream` 建立共享 trace 关联，覆盖 prepare、问题识别、守卫、编排、持久化和总请求耗时。
- [ ] 1.2 为 RAG 检索加入 query rewrite/category、hybrid search、rerank、KG（启用时）、来源元数据查询各自计时及错误/候选数记录。
- [ ] 1.3 为专业模型路线记录每个 Agent/工具的排队、执行、重试/超时，及专业证据检索和总结 LLM 阶段。
- [ ] 1.4 在 LLM 流式调用记录请求开始、首 chunk、结束和失败；保留安全的模型标识与 attempt 数，不记录 prompt/用户敏感内容。
- [ ] 1.5 在 SSE 服务端及前端记录首事件、首 token、done 时间；确认客户端代码位置并将 trace_id 贯通，区分代理网络和浏览器呈现时间。
- [ ] 1.6 按 RAG、单/多模型、综合工作流、恢复交互汇总 p50/p95/p99、错误率、超时率、重试率及阶段耗时，取得生产超过 120 秒请求样本并生成 trace 归因报告。

## 2. 核实阻塞点与部署链路

- [ ] 2.1 对照 trace 检查 SSE `prepare` 在 Response 返回前的同步数据库与上下文解析耗时，并评估完整对话历史读取随会话变长的成本。
- [ ] 2.2 对照实际路由验证 RAG hybrid search、重排、可选知识图谱、来源查询和 LLM 首 chunk 的耗时及是否重复计算。
- [ ] 2.3 对照实际路由确认 Function Calling、AgentManager、LangGraph/综合工作流的调用次数、串行依赖、超时和重试；不得仅凭能力声明推断执行行为。
- [ ] 2.4 核查生产 WSGI/ASGI worker、连接池、代理缓冲、SSE 超时、客户端断连取消和并发排队；验证服务端首 yield 到浏览器收到事件的差值。
- [ ] 2.5 形成根因排序报告，明确观测事实、代码路径风险、线上数据证据、受影响请求比例和待验证假设；无数据支持的项目标记为未知。

## 3. 降低首 token 等待并保护兼容性

- [ ] 3.1 为 SSE 增加向后兼容的阶段 progress 事件，并在 prepare/检索/专业执行/总结等可控边界及时发送；客户端忽略未知事件且不将进度混入答案正文。
- [ ] 3.2 基于阶段数据优化最大耗时组件；对依赖图证明独立的 Agent/任务实施有界并行，保留依赖顺序、部分失败、取消和结果聚合语义。
- [ ] 3.3 基于 trace 处理重复检索/查询、冗余序列化或不必要等待；每项优化提供开关或回退方式并检查权限、来源、空间对象守卫和专业计算结果。
- [ ] 3.4 核验反向代理 SSE 禁缓冲、心跳、读超时和服务器 worker 容量；为长连接配置合理并发与断连资源回收。
- [ ] 3.5 由产品/运维根据实测基线确认分路由 TTFT 与端到端 p95/p99 目标及测量窗口，形成告警阈值和看板。

## 4. 验收

- [ ] 4.1 用可控慢检索、慢 Agent、慢首 chunk、重试、异常、超时及客户端断连场景验证 trace 分段与 progress 事件。
- [ ] 4.2 验证非流式和 SSE 的最终答案、来源、专业模型结果、trace_id、守卫行为及既有 schema 保持兼容。
- [ ] 4.3 在代表性负载下比较优化前后分路由 TTFT、端到端 p50/p95/p99、错误率、资源占用和答案质量，并记录验收结论。
- [ ] 4.4 通过部署链路实测 SSE 首事件/首 token 可见时间，确认代理缓冲和浏览器消费未重新引入长等待。
