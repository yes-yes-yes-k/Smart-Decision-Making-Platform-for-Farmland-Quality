## Context

`POST /api/v1/chat/` 与 `/stream` 共用 `ChatRequestService.prepare`：查询/创建会话、加载完整历史、解析并验证分析上下文、读取可选酸化测算历史，并提交用户消息。`/stream` 完成这些同步步骤后才构造并返回 SSE Response。生成器内先运行 `prepare_routed_state`（状态初始化、问题识别、分析要求守卫），再按路由执行：

- RAG：`_retrieve_documents` 同步进行查询改写、分类、向量/BM25 hybrid search、条件重排，可选知识图谱增强，随后查询来源元数据和组装 prompt；这些工作结束才发来源 meta 或开始 LLM stream。
- 专业模型：先 `execute_models`，再 `retrieve_professional_evidence`，然后总结 LLM stream；所以专业计算和证据检索都位于首 token 前。`AgentManager._execute_with_dependencies` 当前是顺序循环。编排器能力声明可并发最多六个模型，但单纯看到 Manager 的循环不足以证明所有生产专业路径都走该 Manager；应针对实际路由测量。
- 完成阶段：规范化结果、溯源构造、写入助手消息/数据库、序列化并发送 done。非流式路径在 JSON 响应前同步做完整工作。

目前有 RAG 聚合 `latency_ms`、路由日志耗时及 LLM 调用日志，但它们没有形成跨模块的单请求阶段时间线，也不等价于客户端 TTFT。LLM stream 的服务端日志记录整段耗时，未记录首 chunk。仓库代码不能证明生产环境请求超过两分钟的比例；需以线上 trace、访问日志和代理指标验证，而不能把 90 秒 capability timeout、重试声明或某个单项耗时直接当作根因。

## Goals / Non-Goals

**Goals:**

- 建立可按 trace_id 关联的入口、prepare、route、guard、各检索子阶段、Agent/工具、LLM 首 chunk/完成、持久化、首 SSE 写出、请求完成及前端接收阶段数据。
- 分路由计算 p50/p95/p99 TTFT、总时长、阶段占比、失败/超时/重试率，并识别慢请求贡献最大的阶段。
- 为等待超过一个可配置阈值的 SSE 请求发送阶段性进度；维持当前 token、meta、done、error 和响应 schema 兼容。
- 基于测量结果优化真正热点；独立任务并行需遵守数据依赖、资源池和取消语义。

**Non-Goals:**

- 未获得生产 trace 前宣称具体某个服务或模型是“超过两分钟”的统计根因。
- 改变专业计算结果、检索权限/过滤、引用质量、对象守卫或已有聊天响应字段。
- 为追求低延迟而跳过必要的计算/证据、无上限并发或削弱错误语义。
- 仅依靠 SSE 心跳掩盖真实慢路径，或把服务端 yield 时间误当作浏览器呈现时间。

## Decisions

1. **先建阶段 trace，再优化。** 统一使用单调时钟计时，记录 trace_id、conversation_id、路由类型、阶段名、duration、结果状态、attempt 数、候选数量和安全的模型/工具标识；问题正文、提示词和敏感地块数据不进入指标标签。保留现有指标并关联 trace，不重复采样高基数字段。替代方案：直接改超时/并发参数；缺少阶段证据时可能把负载转移到依赖服务，或损害正确性。

2. **明确区分 TTFT 和总时长。** 服务端记录首个 `yield` 前及首 token 的阶段时间；客户端记录请求发起、首事件收到、首 token 呈现和 done 收到。检查代理是否缓冲以及 WSGI worker 是否被长连接占满。替代方案：以接口总时长代表用户等待；该指标无法区分模型慢、首 token 前同步工作或网络缓冲。

3. **在长阶段边界发出语义化进度。** 对 SSE 在准备完成后尽可能早发 `progress` 事件，并在检索/模型阶段边界更新；准备本身若耗时，评估将请求接收后的轻量确认前移。心跳仅用于连接保活，进度不携带内部提示、检索文档或审计数据。替代方案：只发周期性“仍在处理”；虽然可见但不说明阶段且不能减少实际等待。

4. **并发只用于独立工作。** 先从 trace 和依赖图识别可并行的 Agent、检索及后处理；并行节点设置有界并发、共享 deadline、部分失败处理和 request cancellation。保留有依赖的拓扑顺序。现状中专业 Agent Manager 逐个 `analyze`，而 LangGraph spec 提到支持并发，必须在真实请求路径上核对实现，不以规范文本替代运行时证据。

5. **分路由设目标与回归护栏。** RAG、单模型、多模型、综合工作流、needs_input/恢复交互分别建立基线。先记录当前基线，再由产品/运维基于流量和模型能力确认目标阈值；延迟优化必须同时通过回答正确性、来源一致性、权限和专业模型结果验证。

## Risks / Trade-offs

- [埋点增加开销或高基数导致指标成本上升] → 固定阶段名与有限路由标签；trace 采样；避免用户 ID、会话 ID作为 metrics 标签，仅在受控 trace 中关联。
- [并行增加数据库/向量库/模型服务瞬时负载] → 有界 semaphore、队列等待计时、容量压测和可回退开关。
- [进度 SSE 改动破坏现有客户端] → 新增可忽略的事件类型，保持既有事件 payload 和 done 结构不变，并测代理直达与部署代理两种链路。
- [`prepare` 在 Response 建立前同步执行，生成器进度无法覆盖此段] → 将 prepare 子步骤分别计时；必要时把 SSE 响应建立和安全的初始状态提前，但鉴权、校验、用户消息幂等和数据库事务语义必须保留。
- [SSE 连接占用同步服务器 worker] → 对照当前部署服务器 worker 模型、并发和代理读超时评估；是否迁移异步/后台任务由测量结果决定。
- [只有本地代码没有线上分布] → 首阶段交付明确标记“待线上验证”的假设和数据源，避免因单次复现下结论。

## Migration Plan

1. 在开发/测试环境加入阶段事件与前后端时间戳，部署只观测版本，保持执行行为不变。
2. 收集覆盖典型路由、长历史、不同检索命中、模型重试、并发负载及慢请求的基线；按 trace 检查总和与阶段分解是否闭合。
3. 基于最慢阶段逐项启用兼容的进度事件及低风险优化，逐步放量并比较分路由 p50/p95/p99 与答案质量。
4. 回退时关闭优化开关或回滚客户端 progress 处理；观测字段可继续保留，不能依赖删库迁移。
