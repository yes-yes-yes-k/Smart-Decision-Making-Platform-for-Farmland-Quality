# localize-chat-public-fields Design

## Context

模型计算层需要保留稳定字段码，结构化输出契约也需要稳定的英文 snake_case 字段，因此不能在模型结果中直接把所有键替换为中文。问题发生在自然语言生成链路：模型紧凑结果包含内部字段码，LLM 可能照抄；LLM 不可用时，确定性摘要也可能直接格式化字段码；SSE 又可能把一个字段码拆成多个 token。现有综合报告虽有局部映射，但普通聊天和历史消息没有复用。

本设计在“结构化事实”和“用户可见表达”之间增加一层纯展示转换：

```text
版本化模型结果 / 规范模型结果
                │
                ├─ 机器消费者：保持原字段和 JSON 结构
                │
                └─ 用户文本：统一字段字典 → 中文答复/报告/历史消息
```

## Goals / Non-Goals

### Goals

- 用户可见答复不再出现已登记的内部专业字段码。
- 普通聊天、综合报告、非流式、流式和历史消息使用同一词典。
- SSE 字段码跨任意 token 边界拆分时仍正确转换。
- 不影响模型计算、结构化结果、版本化缓存和外部机器调用方。

### Non-Goals

- 不转换未知缩写或普通英文词汇。
- 不翻译模型版本、追溯 ID、单位和外部标准名称。
- 不在本变更中修改旧消息的数据库原文。

## Decisions

### Decision 1: 使用单一公共字段字典

在领域层维护 `PUBLIC_FIELD_LABELS`，按字段真实业务含义定义中文名称。综合报告不得继续维护独立副本；确定性答复、聊天 API 和历史消息读取均复用该字典。

选择单一字典可避免 `SJD` 在一个入口显示为“pH”、另一个入口显示为“土壤酸碱度”等漂移。字典的值面向非技术业务用户，不附加内部代码。

### Decision 2: 只在用户文本边界转换

转换范围限定为：

- 最终 `answer`；
- 综合诊断 `report_draft`；
- 文本型 `recommendations`；
- SSE `token.content`；
- 助手历史消息 `content`；
- 确定性摘要和综合报告正文。

`models`、`chat_compact`、`public_full`、`llm_context` 的结构化键、审计日志和版本化计算结果不做键名转换。这样既改善用户体验，也保持机器契约兼容。

### Decision 3: 提示约束与确定性出口双层防护

最终 LLM prompt 要求只使用中文标准字段名称，降低生成缩写的概率；但 LLM 输出不能视为可信展示格式，HTTP/SSE/持久化出口仍必须执行确定性转换。LLM 不可用时的确定性摘要也必须使用同一转换函数。

### Decision 4: SSE 使用有状态字段识别器

不能逐 token 做简单字符串替换，因为 `GGNL` 可能被拆为 `G`、`GN`、`L`。流式转换器保留尚不能判定的字段前缀，在获得足够字符或流结束后再输出。匹配必须检查左右词边界，避免把 `GGNLcode`、`XGGNL` 等机器标识的一部分误改。

### Decision 5: 历史数据采用读时兼容

新助手消息在持久化前转换。既有记录不执行不可逆批量迁移；消息列表返回和历史上下文构造时转换助手文本。用户消息不转换，避免改写用户原始问题。

## Risks / Trade-offs

- 字典遗漏新字段时仍可能泄漏缩写：新增或变更模型字段时必须同步增加字典项和测试。
- 字段码与普通英文单词同形时可能误替换：只匹配独立词边界，并且只登记明确的业务字段码。
- 流式转换会短暂缓冲可能构成字段码的字符：缓冲长度仅为最长字段码及边界字符，对整体流式体验影响可忽略。
- 历史数据库仍保存旧文本：展示和后续 LLM 上下文均经过转换，保留原文有利于审计且避免数据迁移风险。

## Rollback

回滚时移除用户文本出口的转换调用和流式缓冲器即可。模型结果、数据库结构和版本化计算数据均未变化，不需要数据回滚。已按中文保存的新助手消息保持可读，无需反向恢复为字段码。
