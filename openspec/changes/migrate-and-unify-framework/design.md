## Context

当前存在两个独立项目：
1. **AI_culti_demo -send**: 包含 LangGraph 多智能体工作流、LLM 服务（DeepSeek-V4-Flash）、嵌入服务（bge-large-zh-v1.5）、酸化评估模型、石灰需求量计算等专业模型
2. **org-backend**: 包含 RAG 问答链、Chroma 向量存储、嵌入模型（bge-m3）、数据库模型、JWT 认证、文件上传管理

这两个项目各自独立运行，存在代码重复、配置分散、功能难以协同的问题。需要构建一个统一框架，将两者的核心能力整合，支持六个专业模型的并发处理。

## Goals / Non-Goals

**Goals:**
- 构建统一框架，整合 RAG、Function Calling 和多智能体架构
- 迁移两个项目的核心代码到统一框架
- 支持六个专业模型的并发处理
- 统一 LLM 和 Embedding 服务配置
- 合并 HTTP API 接口
- 保持与原有代码的兼容性

**Non-Goals:**
- 不修改现有已归档的 OpenSpec specs
- 不重构已稳定运行的业务逻辑
- 不引入新的数据库引擎（保持 MySQL）
- 不改变现有数据存储格式

## Decisions

### 1. 架构风格：模块化单体

**选择理由：**
- 项目规模适中，模块化单体便于开发和部署
- 避免微服务带来的运维复杂性
- 模块间通信效率高，适合多智能体并发场景

### 2. 多智能体并发设计

**选择理由：**
- 六个专业模型需要独立运行，并发处理可以显著提升性能
- LangGraph 原生支持异步节点执行

**并发策略：**
- 使用 Python `asyncio` 实现模型并发调用
- LangGraph 节点使用 `@node.async` 装饰器
- 通过状态机协调各模型的执行顺序和依赖关系
- 结果汇总节点等待所有并发模型完成后进行聚合

**并发流程：**
```
用户请求
    │
    ▼
┌──────────────┐
│ 问题识别节点  │
└──────┬───────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│              并发模型执行 (asyncio.gather)                │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌────────────────┐ │
│  │ 模型1   │ │ 模型2   │ │ 模型3   │ │ 模型4-6        │ │
│  │ (酸化)  │ │ (石灰)  │ │ (其他)  │ │ (并行执行)     │ │
│  └────┬────┘ └────┬────┘ └────┬────┘ └───────┬────────┘ │
│       │            │            │              │          │
│       └────────────┴────────────┴──────────────┘          │
│                         │                                 │
│                         ▼                                 │
│              ┌───────────────────┐                        │
│              │  结果聚合节点      │                        │
│              └────────┬──────────┘                        │
└───────────────────────┼───────────────────────────────────┘
                        ▼
                  LLM 生成总结
                        │
                        ▼
                   返回结果
```

### 3. Function Calling 实现：混合方式

**选择理由：**
- LangChain Tools 提供成熟的工具调用机制，适合核心工具
- 自定义接口便于灵活扩展，适合专业模型集成

**实现方案：**
- **核心工具**（文档检索、数据查询）使用 LangChain Tools
- **专业模型**（六个评估模型）使用自定义 JSON Schema 接口
- 通过统一的工具注册表管理所有可调用工具
- LLM 根据工具描述自动选择调用方式

### 4. 嵌入模型统一：支持多模型切换

**选择理由：**
- 两个源项目使用不同的嵌入模型（bge-large-zh-v1.5 vs bge-m3）
- 需要兼容现有向量库数据

**实现方案：**
- 封装统一的 EmbeddingService 接口
- 支持通过配置切换不同嵌入模型
- 提供模型迁移工具，支持向量数据从旧模型迁移到新模型

### 5. HTTP 服务合并：Flask

**选择理由：**
- org-backend 使用 Flask，功能完善
- Flask 支持蓝图（Blueprint），便于模块化组织
- 可以兼容原有 API 接口

**实现方案：**
- 使用 Flask 作为统一 HTTP 框架
- 将原有的 `http.server` 路由迁移到 Flask Blueprint
- 保持原有 API 路径和参数兼容

### 6. 配置管理：环境变量 + 配置文件

**选择理由：**
- 环境变量适合云部署和容器化
- 配置文件便于开发调试

**实现方案：**
- 优先读取环境变量
- 环境变量不存在时读取配置文件
- 支持不同环境（开发/测试/生产）的配置切换

## Risks / Trade-offs

| Risk | Mitigation |
|------|------------|
| 嵌入模型不一致导致向量不兼容 | 提供模型迁移工具，支持数据重新向量化 |
| 并发执行导致资源竞争 | 使用 asyncio 协程，避免共享状态 |
| 代码迁移引入 bug | 保留原有测试用例，逐步迁移验证 |
| API 兼容性问题 | 保持原有 API 路径和参数，新增版本控制 |
| 向量库数据迁移 | 先备份再迁移，提供回滚方案 |
| LLM API 调用失败 | 实现降级机制，缓存常用结果 |

## Migration Plan

1. **Phase 1: 框架搭建**
   - 创建统一框架目录结构
   - 实现核心服务（LLM、Embedding、Vector Store）
   - 配置统一管理

2. **Phase 2: 代码迁移**
   - 迁移 org-backend 的数据库模型和认证系统
   - 迁移 AI_culti_demo 的专业模型和工作流
   - 合并 HTTP API 接口

3. **Phase 3: 集成测试**
   - 验证 RAG 问答功能
   - 验证多智能体并发工作流
   - 验证 Function Calling 功能

4. **Phase 4: 数据迁移**
   - 迁移数据库表结构和数据
   - 迁移向量库数据
